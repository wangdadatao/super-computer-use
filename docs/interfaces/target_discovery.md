## 发现与绑定是两件事

**发现**返回候选列表，不产生任何状态变化，也不需要授权。
**绑定**选定一个目标，产生会话状态，之后所有动作都作用于它。

两者分开的理由：

- 发现在决策之前，应当尽可能廉价。观察到的实现中，
  应用列表这一步明确声明"不需要权限，也不需要屏幕控制"
- 绑定的代价高（占用会话、使旧令牌失效），不应在试探阶段发生
- 调用方经常需要先看列表再决定绑哪个

因此：**发现不需要授权，绑定需要。**

## 应用发现

返回当前正在运行的可操作应用及其窗口。

已知需要处理的性质：

| 性质 | 处理 |
| --- | --- |
| 排序 | 按前台优先排序，让最可能需要绑定的目标排在最前 |
| 窗口 | 一个应用可能有多个窗口，需要能区分；无窗口的应用仍在列表中 |
| 后台进程 | 排除，只列常规应用 |
| 系统 UI | 排除，见下文 |

返回项需要包含足够的稳定标识用于后续绑定：应用标识、进程标识、
以及在多窗口情况下的窗口标识。

## 页面发现

> 状态：设计，未实现。浏览器适配器接入后再落地；当前 `list_windows` 操作的是浏览器窗口，不是页面标签页。

浏览器标签页的发现与应用的差异较大：

- **受控与用户自有要区分**。用户自己打开的标签页与由自动化创建的标签页
  在生命周期归属上不同，不应混为一谈
- **可能跨多个浏览器**。需要能按浏览器过滤
- **URL 不稳定**。标签页导航后 URL 变化，但标签页本身仍是同一个

因此标签页的绑定标识不能是 URL，必须是运行时分配的稳定标识。
URL 只能作为**查找条件**，不能作为身份。

标签页的发现和 claim 由浏览器适配器负责（Playwright MCP / CDP / 扩展 + native host），
不由 macOS AX 层模拟。适配器必须区分用户自有标签页与自动化创建的标签页，
并保留“谁拥有这个标签页”的会话信息。

## 引用形式

绑定请求接受多种引用形式，按明确程度排序：

| 形式 | 明确程度 | 说明 |
| --- | --- | --- |
| 运行时标识 | 最高 | 由发现接口返回，直接命中 |
| 进程标识 + 窗口标识 | 高 | 绕过名称匹配 |
| 应用标识（bundle id 等） | 中 | 唯一时直接命中，多实例时歧义 |
| 显示名称 | 低 | 容易歧义，且在多语言环境下不稳定 |
| URL | 仅用于查找 | 不是身份，需要唯一匹配 |

**名称匹配是兜底，不是首选。** 显示名称会随系统语言变化，
且不同应用可能同名。发现接口返回的稳定标识应当优先使用。

引用形式中，进程标识与窗口标识必须**同时**提供或同时省略。
只提供其一无法唯一确定目标。

## 歧义处理

**歧义一律返回错误，不隐式选择。**

包括：

- 多个应用匹配同一名称
- 多个窗口属于同一应用且未指定窗口标识
- 多个标签页匹配同一 URL

不做"取第一个"或"取最近使用的"的原因：隐式选择在调用方看来
与成功无法区分。调用方以为自己绑定了 A，实际绑定了 B，
之后所有动作都作用在错误的目标上，而且不会收到任何错误信号。

歧义错误的返回值需要包含候选列表，让调用方能够直接选定，
而不需要重新发起发现请求。

## 不可发现的目标

**部分界面元素不是常规应用，不应出现在应用列表中。**

已确认的类别：

| 类别 | 例子 | 理由 |
| --- | --- | --- |
| 系统浮层 | Spotlight、通知中心 | 无常规窗口生命周期，无稳定绑定 |
| 菜单栏额外项 | 状态栏图标 | 属于其他应用的附属 UI，不是独立目标 |
| 实现自身的进程 | SCU 的原生进程 | 自指操作会导致状态不一致 |

这类目标被排除在发现结果之外。尝试绑定它们返回"不存在的目标"，
而不是"不支持"——从调用方的角度，它们不存在于可操作集合中。

**注意：排除不等于无法通过其他途径操作。** 例如菜单栏图标属于
某个应用，通过绑定该应用仍可能触达。排除的是"把它们当作独立目标"。
