# ADR-0025 多窗口：截图与激活使用同一个目标窗口

- **状态**：已接受（实验性）
- **日期**：2026-10-20

<a id="window_target"></a>

## 背景

截图和坐标动作之前都会激活目标应用，但两边原来各自选窗口：

- `ScreenCapture` 选**面积最大**的窗口；
- `WindowActivation` raise **第一个** AX 窗口。

单窗口应用看不出问题；多窗口应用会出现“截图截的是 A，激活的是 B”。
坐标点击按截图的 `windowFrame` 计算全局点，窗口一旦不同，点到的是 B 的同一位置。
这是安全问题，不是显示问题。

## 决策

### 1. 激活时也选“面积最大的非最小化窗口”

`WindowActivation.activate` 枚举 AX 窗口，跳过最小化窗口，按面积取最大；
把选中的窗口 `AXRaise`，并返回它的标题与 frame。

选择规则与截图一致，且是确定性的：不依赖窗口顺序，也不依赖当前 key window。

### 2. 截图只捕获与激活目标匹配的窗口

`WindowActivation` 返回 `Target(title, frame)`；`ScreenCapture` 在
ScreenCaptureKit 的候选窗口里按 frame（容差 2 点）匹配，找不到时：

- 如果目标没有标题和 frame（应用没有可枚举窗口），退回原来的“最大窗口”；
- 否则**拒绝截图**，返回 `platform_unavailable`，不用可能不匹配的窗口。

宁可失败，也不返回一张会点错的图。

### 3. 截图文本带窗口标题

`get_screenshot` 的元数据增加 `title="…"`，让调用方至少能看出截的是哪个窗口。
标题不是身份：同名窗口仍可能混淆；它只是可读线索。

## 取舍

**接受了“最大窗口”这个启发式。** 它不是用户选择，也不保证是用户想要的窗口。
代价是多窗口时可能截到另一个窗口；但它与激活一致，至少不会点错。
真正的窗口选择（按标题/ID 绑定）需要新的协议面，暂不做。

**接受了失败关闭。** 匹配不上就截图失败，而不是退回一个“可能对”的窗口。
这会让少数应用截图失败，但避免坐标动作落到错误窗口。

**没有改变 click/scroll/drag 的 API。** 它们仍然只接收 pid；
窗口选择发生在原生层的激活路径里，对上层透明。

## 后果

- 单窗口应用行为不变；TextEdit 真实验证截图标题与窗口 frame 一致；
- 多窗口应用不再出现“截图 A、激活 B”的已知路径；
- 仍然没有显式窗口选择、窗口列表、跨 Space 的多窗口测试；
- 不改线协议（当时为 v9；后续 ADR-0026 升到 v10）。
