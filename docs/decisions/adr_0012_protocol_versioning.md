# ADR-0012 协议版本在会话建立时协商

- **状态**：已接受
- **日期**：2026-10-16

## 外部观察来源

本文涉及对两套已发布实现的观察结论。来源、具体证据与复核方法见
[verification/external-sources.md](../../verification/external-sources.md)。

## 背景

SCU 至少有两个可能独立演进的部分：

- **接入层与协议层**：对外协议面
- **协议层与原生层**：内部契约

一旦开始分发，就会出现版本错配：用户升级了接入层但原生层仍是旧版，
或者相反。这类错配的症状往往不是明确的报错，而是**行为异常**——
某个字段缺失被当成默认值，某个语义变化被静默接受。

参考实现中观察到一种处理方式：会话建立时双方交换协议版本，
不匹配时明确拒绝连接，并报出双方版本号。

## 决策

**SCU 在两个边界上都做版本一致性检查，不匹配时明确失败，不做隐式兼容。**

### 内部边界：协议层 ↔ 原生层

- 连接建立时交换版本号
- 版本不一致时**拒绝建立会话**，错误中同时给出双方版本
- 版本号是单调递增的整数，不是语义化版本字符串

### 外部边界：agent ↔ 接入层

审计指出外部边界才是错配概率最高处——agent 侧的工具说明、技能与提示词
可能针对某一版 SCU 写成，而运行时的 SCU 已是另一版。

MCP 自身的初始化握手能保证传输层兼容，但**不能保证 SCU 的能力面兼容**。
因此需要一层针对能力的检查：

1. **声明**：接入层在运行时对象上暴露自身的协议版本
2. **可查**：调用方可在工作开始前读取该版本
3. **明确失败**：调用一个当前版本不存在的 API 时，返回
   `protocol_version_mismatch` 错误，**而不是让调用方拿到 `undefined`
   并在后续操作中抛出难以归因的类型错误**

第 3 条是这条决策里最有实际价值的部分。缺失的 API 表现为 `undefined` 时，
调用方看到的是类型错误，无法判断是版本问题、拼写错误还是内部故障。
明确报出 `protocol_version_mismatch` 才能让它做出正确反应。

实现手段是在运行时对象外层加代理：未定义的属性返回一个函数，
调用时抛出该错误，而不是返回 `undefined`。

### 两个边界共同的规则

- 不提供"尽力兼容"模式：不做字段缺失的默认填充，不做未知字段的静默忽略
- 版本不匹配时**明确失败**，不降级运行

**为什么不用语义化版本**：兼容性判断需要的是"能不能通信"这个布尔结论，
而不是"哪个变更等级"。一个整数配合"必须完全相等"的规则，
比解析和比较三段式版本号更简单，也更难误用。

## 取舍

**放弃了向后兼容的便利。** 任何协议变更都要求两侧同时升级。
对开发者体验是负担——不能只升级一侧来试新功能。

**接受了升级期间的不可用。** 版本不匹配时服务完全不可用，
而不是降级运行。这是刻意的：静默降级会掩盖真实的错配。

做出这个取舍的理由：**SCU 处理的是用户真实界面上的真实操作。**
一次因版本错配导致的动作投递到错误位置，后果比一次明确的拒绝严重得多。

## 后果

- 两个边界都需要版本号，且需要明确的版本来源
  （编译期常量，不是运行时可变状态）
- 升级流程需要一个检查点：确认两侧版本一致后再启用会话
- 开发期需要能同时运行多版本的机制，否则本地调试会很痛苦
- **接入层、策略层、协议层同处一个进程，它们之间不需要协商**——
  这一点本文最初表述含糊，实际需要协商的只有
  "协议层 ↔ 原生层"与"agent ↔ 接入层"两条边界
- 外部边界的检查是**软的**：SCU 无法强制 agent 侧校验，
  只能在 API 缺失时给出明确的错误。真正的约束力来自工具说明与技能文档
