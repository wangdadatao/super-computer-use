# ADR-0001 无障碍树优先，视觉坐标为兜底

- **状态**：已接受
- **日期**：2026-10-16

## 背景

桌面自动化有两条技术路线：读取操作系统的无障碍树并按元素操作，
或者截图后用视觉模型估计坐标再注入点击事件。两条路线在成本、
精度和适用范围上差异显著。

在确定 SCU 的方案前，分析了两套已发布实现的行为：OpenAI 的
Codex Computer Use 与 Grok Bot Computer Use。**两者独立地收敛到了同一结论**：

- 都以无障碍树为首选路径，元素表以文本形式提供给模型
- 都把截图 + 坐标明确定位为**兜底**，而非主路径
- 双方的提示词都有同义表述，要求"元素在树里时优先使用元素寻址"

这个独立收敛是重要证据：它说明这不是某一家产品偏好，而是这个问题域下
约束决定的解。

成本差异是主要驱动因素。无障碍树以文本传递，一次完整读取通常在数百行量级；
截图是位图，一张即占用上千 token，且随分辨率上升。

## 决策

**SCU 以无障碍树为主寻址路径，视觉坐标作为显式兜底。**

具体约束：

- 元素表以文本输出，每行一个元素，附稳定引用
- 坐标类动作必须携带坐标令牌，不提供"凭坐标直接点击"的隐式路径
- 无障碍树为空或目标应用不暴露树时，返回明确的可诊断错误，
  而不是静默降级到坐标

## 取舍

**放弃了纯视觉方案的普适性。** 无障碍树的质量完全取决于目标应用是否
正确实现了无障碍暴露。自绘界面的应用（常见于 Electron 与游戏引擎）
可能只暴露极浅的树，甚至完全不暴露。这类应用下 SCU 只能走坐标路径，
效率与精度都低于原生实现良好的应用。

**接受了坐标路径的复杂度。** 如果砍掉坐标兜底，系统会简单很多——
不需要坐标令牌、不需要几何失效判定、不需要截图捕获。保留它意味着
多维护一整套状态。

做出这个取舍的原因：没有任何一个真实应用集合是完全无障碍友好的。
砍掉坐标路径会让 SCU 在相当比例的应用上完全无法工作，
这比多维护一套状态更糟。

## 后果

- 原生层必须实现两条路径：树读取与截图捕获，且两者的失效语义不同
- [快照生命周期](../architecture/snapshot_lifecycle.md)需要管理两种令牌
- 调用方需要有能力判断"该走哪条路"，这属于接入层的职责
- 目标应用的树质量成为 SCU 实际能力的主要变量
