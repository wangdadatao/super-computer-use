# ADR-0013 P0 竖切取代独立验证阶段，验证作为出口门槛

- **状态**：已接受（出口门槛已于 2026-10-16 冻结，见[出口门槛](#出口门槛)）
- **日期**：2026-10-16

## 背景

[本地环境](../operations/local_setup.md)原本规划两个阶段：先用 Python + pyobjc
写一次性脚本验证核心假设（元素身份、令牌失效、收敛判定），再决定实现语言并开工。

重新评估后发现这条路径有两个问题：

- **验证脚本是一次性的。** 采集无障碍树、比对身份键，这些逻辑在实现阶段要用原生语言
  再写一遍。
- **风险被架构隔离了。** 元素身份与令牌失效位于协议层，原生层只是薄封装
  （见[系统总览](../architecture/system_overview.md)的职责边界）。
  假设不成立时，要改的是协议层算法，不是原生层。因此"先实现再验证"的最坏代价是
  改一层，而不是推倒重来。

同时，"设计合理"不等于"假设成立"。[测试策略](../operations/testing.md)列出的假设
仍然未验证。本决策不取消验证，只改变验证发生的位置与时机。

## 决策

### 1. 不设独立验证阶段，验证内嵌为 P0 的出口门槛

P0 是一条**最小竖切**：从读取真实应用的无障碍树，到身份注册、令牌签发与失效检测、
注入一次点击并回报效果摘要。P0 完成的标准**包含**下文的验证门槛，
门槛不通过则 P0 不算完成，不进入后续阶段。

### 2. 技术栈：单一 Swift package

原生层与协议层都用 Swift，放在同一个 package 里，构建与测试只有一套工具链。
同语言的代价是边界要靠模块而不是语言来守住，因此按四层拆成独立 target：

| target | 层 | 承载进程 |
| --- | --- | --- |
| `SCUWire` | 两进程间的线协议：帧、版本、消息类型 | 两者共用 |
| `SCUNative` | 原生层：AX 读取、权限检测 | `scu-native` |
| `SCUCore` | 协议层：句柄注册表、令牌、失效检测 | `scu` |
| `scu` | P0 命令行入口，代替 MCP 接入层 | `scu` |

依赖方向单向：`SCUCore` 不依赖 `SCUNative`，`SCUNative` 不依赖 `SCUCore`，
两者只通过 `SCUWire` 通信。这条约束由 `Package.swift` 强制。

### 3. P0 保留双进程

`scu`（协议层）与 `scu-native`（原生层）从 P0 起就是两个进程，通过 Unix domain socket
上的长度前缀 JSON 帧通信，连接建立时按
[ADR-0012](adr_0012_protocol_versioning.md) 协商版本。

不先合成单进程的理由：进程边界一旦被绕过，就会出现隐式共享状态，
后期拆分的成本高于一开始守住边界。版本错配时明确失败并报出双方版本，
这一行为已由 `HandshakeTests` 覆盖。

### 4. P0 范围

**包含**：权限检测、AX 树读取、元素身份的**度量**（K1~K4 候选键与档位分布，已实现）、
快照令牌与失效分类、点击注入、效果摘要（含收敛判定的最小版本）。
**句柄注册表暂缓**，见下一节。

**不包含**：策略层、虚拟指示层、MCP 接入、code mode 运行时、屏幕捕获与坐标动作、
编辑类操作、浏览器标签页目标、应用知识。这些不影响核心假设，后置。

### 暂缓句柄注册表

句柄注册表（跨快照延续元素句柄）在 P0 内**暂缓实现**，先用数据判断它是否值得做。理由：

- **收益的前提受到质疑。** 审计指出，两家参考实现的提示词都要求每步重读状态，
  调用方手上总是最新引用，句柄延续没有收益；只有"重读之间仍引用旧元素"才需要它。
  这条外部观察尚未在 [verification/external-sources.md](../../verification/external-sources.md) 中核实。
- **代价已经显现。** 仅实现候选键阶段就发现了两处设计错误：K4 不保证唯一（已更正），
  title 抖动不会落到 K3（见[元素身份](../architecture/element_identity.md#已知限制)，待定）。
- **基线数据不支持它。** 访达窗口内可交互元素 93.0% 落入 K4（K1 为 0%）；
  Cursor（Electron）为 51.9%~57.5%。见[基线记录](../../verification/2026-10-16-baseline-identity.md)。
  这是基线而非验证，样本也少，但方向足以暂缓投入。

**决策规则**：只有当正式验证的 K4 结论为「成立」或「部分成立」时，才实现句柄注册表。
结论为「不成立」时，**不实现**，改用**快照内句柄**（每次快照按位置重新编号）加令牌失效检测——
这正是审计 P-07 提出的替代方案。此时 SCU 的差异点收缩为令牌契约、策略与效果回报，
项目定位按下文「门槛失败时的处理」重新评估。

**P0 子集声明**：P0 有意只实现部分契约，以下偏差是已知的，不是遗漏：

| 契约 | P0 实现 | 补齐时机 |
| --- | --- | --- |
| [`ScuError`](../interfaces/error_taxonomy.md#error_structure) | 只有 `code`、`layer`、`retry`、`message`；无 `details`、`candidates` | 出现需要它们的错误（如目标歧义）时 |
| [原生层线协议](../interfaces/native_wire_protocol.md)消息目录 | 4 种请求（握手、权限、应用列表、读树） | 随 P0 动作与令牌工作增加 |
| 未知字段 | 解码时被忽略，版本相等规则兜底 | 待定 |

## 出口门槛

门槛要在**首次采样前**确定，否则验证后再定阈值，容易把标准调到刚好能通过。
项目负责人授权由实现方（本 ADR 作者）制定数值。**以下数值已冻结**：
修改需要在本节追加记录并写明理由，且不得用于重新评判已经执行过的验证。

| 门槛 | 初值 | 对应假设 |
| --- | --- | --- |
| 样本范围 | 至少 3 个应用：2 个原生（含访达）、1 个 Electron | 身份字段稳定 |
| 句柄延续 | [元素身份验证](../operations/testing.md#元素身份验证)的 5 类场景中，预期延续的句柄全部延续 | 身份字段稳定 |
| 句柄唯一 | 同一快照内无两个元素共用句柄 | 身份字段稳定 |
| K4 比例 | 每个样本应用的**窗口内可交互元素**（不含菜单栏）K4 比例：≤ 25% 成立；25%~50% 部分成立；> 50% 不成立。口径与理由见下 | 身份字段稳定 |
| 令牌 | [令牌语义验证](../operations/testing.md#令牌语义验证)的 5 个用例：无漏报，无类别错报 | 令牌失效可检测 |
| 清理 | 连接中断、进程被杀的路径下不残留按下的鼠标按键 | 会话清理 |
| 记录 | 每次验证写 `verification/YYYY-MM-DD-<假设编号>.md`，含采集环境 | 全部 |

### K4 比例的口径与阈值

**度量对象**：K4 比例 = 窗口内可交互元素中，匹配键落在 K4 的个数 ÷ 窗口内可交互元素总数。
（"窗口内"指不在菜单栏子树内，见下方口径 v2 追加记录。）
**逐应用计算，不求平均**，一个应用的好结果不能抵消另一个的坏结果。

**为什么只看可交互元素**：整棵树里有大量 `AXRow`、`AXCell`、`AXGroup` 这类容器，
它们天然没有标识符，必然落入 K4，但 agent 几乎不直接操作它们。
访达的一次手动采样（723 个元素，约 43% 有 `AXIdentifier`）已显示整树口径会被容器拉偏。
整树比例**照常记录，但不参与判定**。

**可交互元素的初始定义**（按 `role`）：`AXButton`、`AXCheckBox`、`AXRadioButton`、
`AXTextField`、`AXTextArea`、`AXComboBox`、`AXPopUpButton`、`AXMenuButton`、
`AXMenuItem`、`AXLink`、`AXSlider`、`AXSearchField`。
`AXNode` 尚未携带 action 列表，定义先按 role 近似；加入 action 后可收紧，修订时按冻结规则记录。

**K1 的计入规则**：形如 `_NS:<数字>` 的 `AXIdentifier` 看起来是 AppKit 自动生成的，
稳定性未知。**判定时不把它们算作显式标识符**（元素按 K2 起算），这是保守口径。
采样时另行记录"若计入"的比例，用于判断这条规则是否过严。

**阈值的依据**：这两个数是判断，**不是**从数据推出来的，因为目前没有可用数据。

| 阈值 | 含义 |
| --- | --- |
| 25% | 每 4 个可操作元素有 1 个靠位置猜时，调用方会频繁遇到 `inferred` 并需要重读，已是明显负担。再高就不应称身份机制"成立" |
| 50% | 过半的可操作元素靠位置猜，"能找回元素"已不再是主要情形，ADR-0004 的核心价值不成立 |

**判定规则**：

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| 成立 | 所有样本应用 ≤ 25% | 保持 ADR-0004 |
| 部分成立 | 无应用 > 50%，但至少一个 > 25% | 继续；启用"更频繁要求重读"的降级；修订 ADR-0004 的风险一节，写明哪类应用受影响 |
| 不成立 | 任一应用 > 50% | 记录该应用；若**半数及以上**样本应用不成立，触发下文的项目定位重新评估 |

**基线先行**：正式验证前先跑一次基线，只统计各键档位分布，**不判成败**。
基线用于检查口径本身有没有错（例如角色清单漏了常见控件），**不用于调整上面的数值**。
口径的修订需要追加记录。

**口径 v2 追加记录（2026-10-16，基线之后）**：基线发现原口径被菜单栏淹没——
终端 322 个"可交互元素"中 320 个是菜单项，Cursor 210 个中 204 个，访达 398 个中 332 个。
比例实际在度量菜单栏，而不是 agent 要操作的窗口控件。修订：

1. **可交互元素不含菜单栏子树**（祖先含 `AXMenuBar` 的元素）。菜单栏另计，不参与判定。
2. **窗口内可交互元素少于 20 个的应用不具统计意义**，不参与判定，需换样本。20 是判断值，不是推出的数。
3. `AXDescription` 作为 K2 标签的口径列为**实验**，并列统计，不进入判定；基线显示它对 K4 比例的改善有限。

**阈值数值（25% / 50%）与判定规则不变**，本次修订只改变度量对象，不改变标准。
修订原因是口径本身有缺陷，不是因为数值难以通过——访达在新口径下反而从 42.2% 升到 93.0%。

### 门槛失败时的处理

| 失败项 | 降级方案 | 项目是否继续 |
| --- | --- | --- |
| K4 比例过高 | 接受较低稳定性，更频繁要求重读；回头修订 [ADR-0004](adr_0004_stable_element_identity.md) | 继续，但核心差异点缩小为"能感知元素移动"，需要重新评估项目定位 |
| 令牌误报多 | 收紧检测条件，或把一部分失效改为"尽力而为" | 继续，但需评估对可用性的影响 |
| 令牌漏报 | 不可接受（会放行错误动作） | 必须修复才能继续，没有降级方案 |
| 清理不到位 | 不可接受（会影响用户使用电脑） | 必须修复才能继续，没有降级方案 |

**元素身份失败不会让项目作废**，但它是 SCU 相对既有实现的核心差异点，
失败后需要重新判断项目是否仍然值得做。这个判断点在此提前写明，不留到失败之后。

## v1 范围（草案）

P0 是第一个竖切，不是产品。审计指出文档描述了一个完整系统却没有 v1 边界，这里补上。
用户的主要痛点尚不明确（可靠性、覆盖、速度与成本均未定），所以 v1 取**最小可用**：
能在原生应用上可靠地读、点、输入，并知道状态是否过期。**本节是草案**，随 P0 数据修订。

| 类别 | 内容 |
| --- | --- |
| **v1 包含** | 权限检测；文本化元素表；快照令牌与失效检测；点击、输入、设值；最小效果回报（已投递、树是否变化）；固定短等待，界面仍在变化时延长，有总上限；极简拒绝清单（终端类应用、SCU 自身）；MCP stdio 的 `js` / `js_reset` 或等价的最小工具面 |
| **设计保留、v1 不实现** | 句柄跨快照延续（见上，取决于数据）；收敛判定的完整机制（树版本号、变更通知、静默阈值、显式等待原语、三态）；虚拟指示层；审批 UI、双作用域与审计记录；坐标兜底与截图；浏览器标签页目标；应用知识库；完整错误码表（按实际需要增长） |
| **明确不做** | Linux、Windows；UI 自动化之外的领域能力（见 [ADR-0010](adr_0010_ui_automation_only.md)） |
| **待定** | v1 是否带 code mode 运行时，还是先只做命令行；agent 使用指导（工具描述与技能文档，审计 P-02）放在 v1 还是紧随其后；分发方式 |

"设计保留"的文档**不删除**：它们是设计依据，也是后续阶段的输入。
但它们描述的是拟实施设计，在各自被实现并验证前，不得读作已实现行为。

## 取舍

**放弃了先验证再投入的保守性。** 若身份假设不成立，P0 中围绕身份写的协议层代码
有一部分要重写。接受这一点，是因为隔离的存在使重写范围有界，
且这部分代码本来就是验证的载体，不是额外成本。

**接受了 P0 期间实现与假设同时漂移。** 边写边验证容易让实现迁就样本。
缓解办法是门槛提前冻结，并把验证结论写进 `verification/`，而不是只留在代码里。

**接受了 Swift 工具链的绑定。** 协议层与未来的 JS 运行时（[运行时契约](../interfaces/runtime_contract.md)）
可能不同语言，该选择仍然待定，不由本决策限定。

## 后果

- [本地环境](../operations/local_setup.md)不再要求先建立 Python 验证环境
- `Package.swift` 与 `Sources/` 成为仓库的一部分，文档需区分"已实现行为"与"拟实施设计"
- 新增构建与测试步骤，见本地环境
- [测试策略](../operations/testing.md)的假设表仍然有效，执行时机改为 P0 内
- 原生层语言不再是[系统总览](../architecture/system_overview.md)中的待定项
