# ADR-0013 P0 竖切取代独立验证阶段，验证作为出口门槛

- **状态**：已接受（出口门槛已于 2026-10-16 冻结，见[出口门槛](#出口门槛)）
- **日期**：2026-10-16

## 背景

[本地环境](../operations/local_setup.md)原本规划两个阶段：先用 Python + pyobjc
写一次性脚本验证核心假设（元素身份、令牌失效、收敛判定），再决定实现语言并开工。

重新评估后发现这条路径有两个问题：

- **验证脚本是一次性的。** 采集无障碍树、比对身份键，这些逻辑在实现阶段要用原生语言
  再写一遍。
- **风险被架构隔离了。** 元素身份与令牌失效位于协议层，原生层只是薄封装
  （见[系统总览](../architecture/system_overview.md)的职责边界）。
  假设不成立时，要改的是协议层算法，不是原生层。因此"先实现再验证"的最坏代价是
  改一层，而不是推倒重来。

同时，"设计合理"不等于"假设成立"。[测试策略](../operations/testing.md)列出的假设
仍然未验证。本决策不取消验证，只改变验证发生的位置与时机。

## 决策

### 1. 不设独立验证阶段，验证内嵌为 P0 的出口门槛

P0 是一条**最小竖切**：从读取真实应用的无障碍树，到身份注册、令牌签发与失效检测、
注入一次点击并回报效果摘要。P0 完成的标准**包含**下文的验证门槛，
门槛不通过则 P0 不算完成，不进入后续阶段。

### 2. 技术栈：单一 Swift package

原生层与协议层都用 Swift，放在同一个 package 里，构建与测试只有一套工具链。
同语言的代价是边界要靠模块而不是语言来守住，因此按四层拆成独立 target：

| target | 层 | 承载进程 |
| --- | --- | --- |
| `SCUWire` | 两进程间的线协议：帧、版本、消息类型 | 两者共用 |
| `SCUNative` | 原生层：AX 读取、权限检测、沿路径定位与 `AXPress`（`AXLocator`） | `scu-native` |
| `SCUCore` | 协议层：会话与令牌、按路径定位句柄、失效检测、拒绝类目、收敛与效果摘要（句柄注册表**不实现**，见下） | `scu` |
| `SCUMCP` | 接入层：MCP stdio 服务（默认只读，`--actions` 加 `click`），只依赖协议层 | `scu` |
| `scu` | 命令行入口：诊断命令与 `scu mcp` | `scu` |
| `scu-fixture` | 验证用夹具应用，不是产品的一部分，不是 product | 独立进程 |

依赖方向单向：`SCUCore` 不依赖 `SCUNative`，`SCUNative` 不依赖 `SCUCore`，
两者只通过 `SCUWire` 通信。这条约束由 `Package.swift` 强制。

### 3. P0 保留双进程

`scu`（协议层）与 `scu-native`（原生层）从 P0 起就是两个进程，通过 Unix domain socket
上的长度前缀 JSON 帧通信，连接建立时按
[ADR-0012](adr_0012_protocol_versioning.md) 协商版本。

不先合成单进程的理由：进程边界一旦被绕过，就会出现隐式共享状态，
后期拆分的成本高于一开始守住边界。版本错配时明确失败并报出双方版本，
这一行为已由 `HandshakeTests` 覆盖。

### 4. P0 范围

**包含**：权限检测、AX 树读取、元素身份的**度量**（K1~K4 候选键与档位分布，已实现）、
快照令牌与失效分类、点击注入、效果摘要（含收敛判定的最小版本）。
**句柄注册表暂缓**，见下一节。

**不包含**：策略层、虚拟指示层、MCP 的动作工具、code mode 运行时、屏幕捕获与坐标动作、
编辑类操作、浏览器标签页目标、应用知识。这些不影响核心假设，后置。

### 暂缓句柄注册表

句柄注册表（跨快照延续元素句柄）在 P0 内**暂缓实现**，先用数据判断它是否值得做。理由：

- **收益的前提受到质疑。** 审计指出，两家参考实现的提示词都要求每步重读状态，
  调用方手上总是最新引用，句柄延续没有收益；只有"重读之间仍引用旧元素"才需要它。
  这条外部观察尚未在 [verification/external-sources.md](../../verification/external-sources.md) 中核实。
- **代价已经显现。** 仅实现候选键阶段就发现了两处设计错误：K4 不保证唯一（已更正），
  title 抖动不会落到 K3（见[元素身份](../architecture/element_identity.md#已知限制)，待定）。
- **基线数据不支持它。** 访达窗口内可交互元素 93.0% 落入 K4（K1 为 0%）；
  Cursor（Electron）为 51.9%~57.5%。见[基线记录](../../verification/2026-10-16-baseline-identity.md)。
  这是基线而非验证，样本也少，但方向足以暂缓投入。

**决策规则**：只有当正式验证的 K4 结论为「成立」或「部分成立」时，才实现句柄注册表。
结论为「不成立」时，**不实现**，改用**快照内句柄**（每次快照按位置重新编号）加令牌失效检测——
这正是审计 P-07 提出的替代方案。此时 SCU 的差异点收缩为令牌契约、策略与效果回报，
项目定位是否重新评估，以 [ADR-0014](adr_0014_positioning_ai_usability.md) 为准（本段原先指向下文的「门槛失败时的处理」，已被取代，见[追加记录](#追加记录2026-10-18定位澄清之后)）。

**P0 子集声明**：P0 有意只实现部分契约，以下偏差是已知的，不是遗漏：

| 契约 | P0 实现 | 补齐时机 |
| --- | --- | --- |
| [`ScuError`](../interfaces/error_taxonomy.md#error_structure) | 只有 `code`、`layer`、`retry`、`message`；无 `details`、`candidates` | 出现需要它们的错误（如目标歧义）时 |
| [原生层线协议](../interfaces/native_wire_protocol.md)消息目录 | P0 时为 5 种请求（握手、权限、应用列表、读树、`performAction`；协议版本 3）；v1 加了 `typeText` / `pressKey` / `setValue`，版本 5；v2 继续加入 `captureWindow`、`AXNode.actions`、`clickAt`、`scrollAt`、`dragAt`、`listWindows` 与窗口根，协议至 v11 | 随 P0 动作与令牌工作增加 |
| 未知字段 | 解码时被忽略，版本相等规则兜底 | 待定 |

## 出口门槛

门槛要在**首次采样前**确定，否则验证后再定阈值，容易把标准调到刚好能通过。
项目负责人授权由实现方（本 ADR 作者）制定数值。**以下数值已冻结**：
修改需要在本节追加记录并写明理由，且不得用于重新评判已经执行过的验证。

| 门槛 | 初值 | 对应假设 |
| --- | --- | --- |
| 样本范围 | 至少 3 个应用：2 个原生（含访达）、1 个 Electron | 身份字段稳定 |
| 句柄延续 | [元素身份验证](../operations/testing.md#元素身份验证)的 5 类场景中，预期延续的句柄全部延续 | 身份字段稳定 |
| 句柄唯一 | 同一快照内无两个元素共用句柄 | 身份字段稳定 |
| K4 比例 | 每个样本应用的**窗口内可交互元素**（不含菜单栏）K4 比例：≤ 25% 成立；25%~50% 部分成立；> 50% 不成立。口径与理由见下 | 身份字段稳定 |
| 令牌 | [令牌语义验证](../operations/testing.md#令牌语义验证)的 5 个用例：无漏报，无类别错报 | 令牌失效可检测 |
| 清理 | 连接中断、进程被杀的路径下不残留按下的鼠标按键 | 会话清理 |
| 记录 | 每次验证写 `verification/YYYY-MM-DD-<假设编号>.md`，含采集环境 | 全部 |

### K4 比例的口径与阈值

**度量对象**：K4 比例 = 窗口内可交互元素中，匹配键落在 K4 的个数 ÷ 窗口内可交互元素总数。
（"窗口内"指不在菜单栏子树内，见下方口径 v2 追加记录。）
**逐应用计算，不求平均**，一个应用的好结果不能抵消另一个的坏结果。

**为什么只看可交互元素**：整棵树里有大量 `AXRow`、`AXCell`、`AXGroup` 这类容器，
它们天然没有标识符，必然落入 K4，但 agent 几乎不直接操作它们。
访达的一次手动采样（723 个元素，约 43% 有 `AXIdentifier`）已显示整树口径会被容器拉偏。
整树比例**照常记录，但不参与判定**。

**可交互元素的初始定义**（按 `role`）：`AXButton`、`AXCheckBox`、`AXRadioButton`、
`AXTextField`、`AXTextArea`、`AXComboBox`、`AXPopUpButton`、`AXMenuButton`、
`AXMenuItem`、`AXLink`、`AXSlider`、`AXSearchField`。
`AXNode` 尚未携带 action 列表，定义先按 role 近似；加入 action 后可收紧，修订时按冻结规则记录。

**K1 的计入规则**：形如 `_NS:<数字>` 的 `AXIdentifier` 看起来是 AppKit 自动生成的，
稳定性未知。**判定时不把它们算作显式标识符**（元素按 K2 起算），这是保守口径。
采样时另行记录"若计入"的比例，用于判断这条规则是否过严。

**阈值的依据**：这两个数是判断，**不是**从数据推出来的，因为目前没有可用数据。

| 阈值 | 含义 |
| --- | --- |
| 25% | 每 4 个可操作元素有 1 个靠位置猜时，调用方会频繁遇到 `inferred` 并需要重读，已是明显负担。再高就不应称身份机制"成立" |
| 50% | 过半的可操作元素靠位置猜，"能找回元素"已不再是主要情形，ADR-0004 的核心价值不成立 |

**判定规则**：

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| 成立 | 所有样本应用 ≤ 25% | 保持 ADR-0004 |
| 部分成立 | 无应用 > 50%，但至少一个 > 25% | 继续；启用"更频繁要求重读"的降级；修订 ADR-0004 的风险一节，写明哪类应用受影响 |
| 不成立 | 任一应用 > 50% | 记录该应用；若**半数及以上**样本应用不成立，触发下文的项目定位重新评估（**已被 ADR-0014 取代**：重新评估不再由 K4 触发，见[追加记录](#追加记录2026-10-18定位澄清之后)） |

**基线先行**：正式验证前先跑一次基线，只统计各键档位分布，**不判成败**。
基线用于检查口径本身有没有错（例如角色清单漏了常见控件），**不用于调整上面的数值**。
口径的修订需要追加记录。

**口径 v2 追加记录（2026-10-16，基线之后）**：基线发现原口径被菜单栏淹没——
终端 322 个"可交互元素"中 320 个是菜单项，Cursor 210 个中 204 个，访达 398 个中 332 个。
比例实际在度量菜单栏，而不是 agent 要操作的窗口控件。修订：

1. **可交互元素不含菜单栏子树**（祖先含 `AXMenuBar` 的元素）。菜单栏另计，不参与判定。
2. **窗口内可交互元素少于 20 个的应用不具统计意义**，不参与判定，需换样本。20 是判断值，不是推出的数。
3. `AXDescription` 作为 K2 标签的口径列为**实验**，并列统计，不进入判定；基线显示它对 K4 比例的改善有限。

**阈值数值（25% / 50%）与判定规则不变**，本次修订只改变度量对象，不改变标准。
修订原因是口径本身有缺陷，不是因为数值难以通过——访达在新口径下反而从 42.2% 升到 93.0%。

### 追加记录（2026-10-18，定位澄清之后）

[ADR-0014](adr_0014_positioning_ai_usability.md) 把定位明确为"对 AI 更好用"。核对出口门槛时发现下列几项
与"暂缓句柄注册表"和 P0 范围不一致。**以下所有门槛都还没有执行过任何验证**，所以修订不会重新评判任何已执行的结果。

| 门槛 | 原表述 | 追加后 | 理由 |
| --- | --- | --- | --- |
| 句柄延续 | 5 类场景中预期延续的句柄全部延续 | **暂停，不适用**；决定实现注册表时恢复 | 没有注册表就没有跨快照的延续可验 |
| 句柄唯一 | 同一快照内无两个元素共用句柄 | 改为**同一次读取内**句柄唯一 | 快照内句柄是先序编号，天然唯一，但仍要有测试守住 |
| 令牌 | 5 个用例 | **P0 内 4 个**：有效不误报、界面变化后旧令牌拒绝且分类为树变化、切换目标后旧令牌拒绝、重复使用失效令牌只上报一次。"窗口移动后旧坐标令牌"移出，随坐标动作 | P0 不含坐标动作，没有坐标令牌 |
| 清理 | 连接中断、进程被杀的路径下不残留按下的鼠标按键 | **条件适用**，取决于点击的实现方式（待定，见 P0 动作档）。若点击只经 `AXPress`，不产生按住状态，该门槛记为"不适用"并写明理由，**不记为通过**；若用合成鼠标事件，全部适用 | 门槛的前提是存在"按下未释放"的状态 |
| 效果摘要与收敛 | 未列为门槛 | **已定（2026-10-19，见下方[追加记录](#gate_revision_2026_10_19)）**：效果摘要按修订后的口径列为门槛；收敛不列为门槛，两秒加载记为已知限制 | 它是 P0 内要做的功能，却不是通过 P0 的条件，这是遗漏还是有意，需要项目负责人确认。2026-10-19 已确认，见下 |
| 项目定位重新评估 | K4 半数应用不成立时触发 | 由 ADR-0014 的度量取代，**待阈值冻结时写定** | 身份不再是项目存在的理由 |

样本范围、K4 比例与记录三项不变。

### 追加记录（2026-10-18，句柄解析与令牌实现之后）

[ADR-0015](adr_0015_handle_resolution_by_path.md) 定下了动作寻址与令牌语义。对上表的影响：

- **令牌第 4 项**"重复使用失效令牌只上报一次"按 ADR-0015 §4 解释：**每次使用都被拒绝，失效迁移只记一次**。
  这是对歧义的澄清，不是放宽——放行一次失效令牌的动作就是漏报。
- **令牌 4 个用例的实现状态**（会话层，假读取器，`SessionTests`）：有效不误报（结构不变复用令牌、几何变化不失效）、
  变化后旧令牌拒绝且分类为 `stale_snapshot`、切换目标后旧令牌拒绝且分类为 `target_switched`、重复使用失效令牌。
  另有真实访达上的两项：对约 200 个句柄做 `verify` 全部通过（界面未变时无误拒），篡改子节点数与核对键均被判失效。
- **尚未度量**：动态界面下的误拒率（ADR-0015 的取舍把它留给验证阶段）；`press` 在真实应用上的投递。
  这两项属于步骤 4（夹具应用与正式验证），在那之前"令牌"门槛**不记为通过**。

| 动作效果（5 个场景） | **部分满足** | 遮挡一行不成立（`AXPress` 不看遮挡）；输入一行不适用（无输入动作） |
| 收敛（前 4 个场景） | **未满足** | 两秒加载被两次一致的判定错过；缺口已用 `withKnownIssue` 固定 |

要么经单独决策修订该行的期望（修订须追加记录并写明理由，且不得用于重新评判已经执行过的验证）。

### 追加记录（2026-10-18，K4 正式验证之后）

结果见 [verification/2026-10-18-identity-k4.md](../../verification/2026-10-18-identity-k4.md)：
访达 54.2%（窗口内 24 个）、活动监视器 48.4%（31 个）、Cursor 57.9%（114 个，Electron）。
按冻结规则（任一应用 > 50%）结论为**不成立**；样本范围门槛（2 原生含访达 + 1 Electron）满足，但样本量小、窗口状态与 Electron 预热未受控。

- **句柄注册表**：按上文"决策规则"**不实现**，保持快照内句柄加令牌失效检测（ADR-0015）。
- **句柄延续**门槛：随注册表暂停，不适用。**句柄唯一**门槛（同一次读取内）：句柄是先序编号，由 `SessionTests` 守住。
- **项目定位**：不因此重新评估（ADR-0014）。
- 不改动冻结的阈值与口径。验证中发现 `description` 若计入匹配键会明显降低 K4（访达 54.2%→12.5%，活动监视器 48.4%→25.8%，Cursor 57.9%→39.5%），
  这是对口径的**改进线索**，不用来重新评判本次结果；是否采用另行决策。

### 追加记录（2026-10-19，收敛项与效果项的口径）

上方[2026-10-18 追加记录](#追加记录2026-10-18定位澄清之后)里留了"效果摘要与收敛是否列为门槛"这个待定项，本次决定。
本次不改动任何门槛数值与度量口径，也不重新评判已经执行过的验证。

**1. 效果摘要列为出口门槛。** 判定范围是[测试策略](../operations/testing.md#动作效果验证)的五个场景，口径按下表修订：

| 场景 | P0 的判定 |
| --- | --- |
| 点击可用按钮 | `treeChanged=true`、`noOpSuspected=false` |
| 点击禁用按钮 | `noOpSuspected=true`。平台可能不报错，"投递成功"不等于有效果 |
| 点击被遮挡的元素 | **按实测修订期望**：`AXPress` 不看遮挡，照常按下并产生效果。"拒绝或疑似空操作"的旧期望作废 |
| 在只读输入框输入 | P0 不适用：没有输入动作 |
| 点击后触发耗时加载 | 并入下面的收敛项，不作为效果项判定 |

按修订后的口径，夹具上已记录的行为使**动作效果项记为满足**：可用按钮、禁用按钮、遮挡三项均为实测行为，
输入不适用，耗时加载不在此项。这不修改 2026-10-18 记录里"与旧期望不符"的原始结论，也不重新评判它。

**2. 收敛判定不列为出口门槛，两秒加载记为已知限制。** 理由：

- P0 的收敛是无加载信号的最小判定（200 毫秒轮询、连续两次一致、3 秒上限），
  局限已在 [ADR-0011](adr_0011_convergence_over_fixed_delay.md) 写明：两次一致只说明 400 毫秒内没变。
- 修它需要**加机制**（加载信号、显式等待原语或明显更长的观察窗口），不是调参，属 v1。
- 已执行的夹具验证结论**保持"未满足"**，不因本次修订改记为通过。

P0 内仍要求收敛的这三项成立，且由 `FixtureTests` 覆盖：立即变化 → 已收敛・有变化；
无限动画 → 到上限返回未收敛且不无限等待；后台繁忙但界面不变 → 已收敛・无变化（已知局限，不要求区分）。

**3. 令牌门槛的误拒率度量方法定下。** 门槛本身不变（4 个用例无漏报、无类别错报），
补测的误拒在受控夹具上量四项，脚本为 `scripts/measure_token_reject.py`：

| 指标 | 构造 | 期望 |
| --- | --- | --- |
| A 无外部变化时重复动作 | 同一令牌连续点击空操作按钮 | 0 次拒绝 |
| B 外部值变化后动作 | 另一会话改变标签文字（路径不变），再动作 | 0 次拒绝 |
| C 外部结构变化后动作 | 另一会话加一个兄弟节点，再动作 | 按 ADR-0015 的取舍预期被拒；记下比例，这是代价不是缺陷 |
| D 自身点击后的令牌失效 | 用同一令牌点击会改值的按钮 | 记录失效与重读次数，作为"每次动作都要重读"的成本 |

真实应用上的同类度量随"第三方应用 `AXPress`"与"经宿主调用 `click`"两项一起做。
在脚本执行并写入 `verification/` 之前，「令牌」门槛**仍不记为通过**。

<a id="token_rate_2026_10_19"></a>

### 追加记录（2026-10-19，令牌误拒率度量之后）

结果见 [verification/2026-10-19-token-reject-rate.md](../../verification/2026-10-19-token-reject-rate.md)：
受控夹具上 A（无外部变化）0/8 被拒、B（外部值变化）0/8 被拒、C（外部结构变化）8/8 被拒、
D（自身改值点击）8/8 令牌失效并需要重读。

- **「令牌」门槛记为通过。** 四个用例的语义此前已成立（见 2026-10-18 的两条记录），
  本次补上误拒的受控数据：没有外部变化、只是取值变化时都不误拒，也没有漏报或类别错报。
  C 的拒绝是 ADR-0015 的保守取舍（目标本身没变），不是缺陷；它的真实发生频率是成本问题，
  与"机制是否正确"分开，不列为门槛。
- **真实应用上的误拒率与发生频率仍未度量**，并入"第三方应用 `AXPress`"与"经宿主调用 `click`"两项，
  作为 P0 之后的观察项，不阻塞门槛。
- 本条不改动冻结的阈值与口径，也不重新评判已经执行过的验证。

**出口门槛现状**（含此前各条的结论）：

| 门槛 | 状态 |
| --- | --- |
| 样本范围 | 满足（访达、活动监视器、Cursor） |
| 句柄延续 | 不适用（注册表不实现） |
| 句柄唯一 | 满足（`SessionTests`） |
| K4 比例 | 已执行，结论不成立；按决策规则不实现注册表 |
| 令牌 | **通过**（本条） |
| 清理 | 不适用（只用 `AXPress`，无按下未释放状态） |
| 效果摘要 | 满足（2026-10-19 口径修订） |
| 收敛 | 不列为门槛（两秒加载记为已知限制） |
| 记录 | 满足（`verification/` 五份记录） |

按本 ADR 的定义，P0 的出口门槛**已全部满足或经记录判定不适用**。项目负责人已于 2026-10-19 确认 P0 完成；
v1 范围仍是草案。

### 门槛失败时的处理

| 失败项 | 降级方案 | 项目是否继续 |
| --- | --- | --- |
| K4 比例过高 | 接受较低稳定性，更频繁要求重读；回头修订 [ADR-0004](adr_0004_stable_element_identity.md) | 继续；**项目定位不再因此重新评估**（见[追加记录](#追加记录2026-10-18定位澄清之后)与 [ADR-0014](adr_0014_positioning_ai_usability.md)），只决定是否实现句柄注册表 |
| 令牌误报多 | 收紧检测条件，或把一部分失效改为"尽力而为" | 继续，但需评估对可用性的影响 |
| 令牌漏报 | 不可接受（会放行错误动作） | 必须修复才能继续，没有降级方案 |
| 清理不到位 | 不可接受（会影响用户使用电脑） | 必须修复才能继续，没有降级方案 |

**元素身份失败不会让项目作废。** 本段原先写"它是 SCU 相对既有实现的核心差异点，失败后需要重新判断项目是否仍然值得做"，
该前提已被 [ADR-0014](adr_0014_positioning_ai_usability.md) 取代：项目目标是对 AI 更好用，身份只是手段之一。
重新评估的触发条件改为基于 ADR-0014 的度量，**待阈值冻结时写定**。

真实任务集 6 个：5 个通过、1 个部分通过（访达内联重命名）；多窗口输入与选区委缩两个 bug 已修。

## v1 范围（草案）

P0 是第一个竖切，不是产品。审计指出文档描述了一个完整系统却没有 v1 边界，这里补上。
用户的主要痛点尚不明确（可靠性、覆盖、速度与成本均未定），所以 v1 取**最小可用**：
能在原生应用上可靠地读、点、输入，并知道状态是否过期。**本节是草案**，随 P0 数据修订。

| 类别 | 内容 |
| --- | --- |
| **v1 包含** | 权限检测；文本化元素表；快照令牌与失效检测；点击、输入、设值；最小效果回报（已投递、树是否变化）；固定短等待，界面仍在变化时延长，有总上限；极简拒绝清单（终端类应用、SCU 自身）；MCP stdio 的 `js` / `js_reset` 或等价的最小工具面 |
| **设计保留、v1 不实现** | 句柄跨快照延续（见上，取决于数据）；收敛判定的完整机制（树版本号、变更通知、静默阈值、显式等待原语、三态）；虚拟指示层；审批 UI、双作用域与审计记录；坐标兜底与截图；浏览器标签页目标；应用知识库；完整错误码表（按实际需要增长） |
| **明确不做** | Linux、Windows；UI 自动化之外的领域能力（见 [ADR-0010](adr_0010_ui_automation_only.md)） |
| **已定** | **2026-10-19**：v1 **不引入 code mode**，用平铺 MCP 工具（等价最小工具面；code mode 后置到 v2，方向不变，见 [ADR-0002](adr_0002_code_mode_surface.md)）；**v1 不做分发**，只支持源码构建（见 [INSTALL.md](../../skills/scu/INSTALL.md)）；agent 使用指导已补（[SKILL.md](../../skills/scu/SKILL.md)） |

**v1 进度（2026-10-19）**：读取、点击、输入（`type_text` / `press_key`）与设值（`set_value`）已实现，
见 [ADR-0016](adr_0016_input_and_keys.md)；坐标动作、滚动与拖拽、应用启动、指示环、连接级应用允许列表已实现；逐次审批、code mode 未开始。
真实应用验证已完成一次（网易云，CEF + 无障碍启动参数），见
[verification/2026-10-19-real-app-netease.md](../../verification/2026-10-19-real-app-netease.md)。

"设计保留"的文档**不删除**：它们是设计依据，也是后续阶段的输入。
但它们描述的是拟实施设计，在各自被实现并验证前，不得读作已实现行为。

### 追加记录（2026-10-19，v1 收口）

v1 的功能点与验证已完成，版本号定为 **0.1.0**。两项待定按项目负责人决定关闭：

- **code mode 不进 v1。** 平铺工具已满足「等价的最小工具面」，实际接入与验证也走平铺工具；
  code mode 需要 JS 运行时与沙箱设计，后置到 v2。[ADR-0002](adr_0002_code_mode_surface.md) 的方向不变。
- **v1 不做分发。** 只支持源码构建（[INSTALL.md](../../skills/scu/INSTALL.md)）。
  理由：真实应用覆盖还只有一个（网易云，且需要 CEF 启动参数），打包、签名/公证与权限引导都未成熟；
  现在发布分发包会给人"可以直接用"的错误预期。何时补：真实应用覆盖扩大、打包方案确定后。

v1 的完成范围：读取、点击、输入（逐字/按键）、设值、令牌与失效、效果回报、拒绝清单、平铺 MCP 工具、
agent 使用与安装指导、一次真实第三方应用端到端验证。真实应用覆盖与输入法仍是已知缺口，见
[测试策略](../operations/testing.md#当前状态)。

<a id="v2_candidates_2026_10_19"></a>

### v2 候选（草案，未决策）

v1 收口后按缺口排的候选范围。**这是草案**，开工前要把选中项写成正式范围并定度量方式
（[ADR-0014](adr_0014_positioning_ai_usability.md)）。

**2026-10-20 状态**：截图+坐标、滚动/拖拽、应用启动/窗口目标、连接级允许列表与指示层已实现；
逐次审批经参考实现调研后决定不做（见 [审批触发](../../verification/2026-10-20-approval-triggers.md)）；
OCR、CEF 产品化、IME、`batch`、code mode 与分发仍未做。

| 候选 | 目的 | 主要代价 |
| --- | --- | --- |
| **截图 + 坐标**（几何令牌、坐标点击/滚动/拖拽、虚拟指示层） | 覆盖不暴露 AX 的应用（非 CEF 自绘、画布、部分游戏） | 屏幕录制权限；坐标脆性；验证弱；需要指示层 |
| **OCR（Vision）**（可选增强） | 截图上的文字 → 候选框，让模型按文字选 ID；只对文字有效 | 不判断可点击性；图标/画布无效；v2 第一版不做 |
| **滚动、拖拽** | 长列表与画布操作 | 依赖坐标或可滚动元素；需要新的效果判定 |
| **应用启动 / 窗口目标** | 现在只能操作已在运行的应用 | 进程生命周期、目标绑定、权限与策略 |
| **应用允许列表 + 指示层** | 限制可操作应用；用户看得见 AI 在做什么 | 配置面与录制排除；策略层扩展 |
| **逐次审批** | 危险动作可确认 | 交互面；参考实现主要用应用级审批，是否值得另做待定 |
| **CEF 适配产品化** | 把 [ADR-0017](adr_0017_cef_accessibility_launch.md) 的手动步骤变成可复用流程 | 需要检测、用户同意、重启状态恢复 |
| **真实应用覆盖与 IME** | 现在只有一个真实应用（网易云）与中文直接输入 | 每个应用的树差异、输入法行为 |
| **接口演进：`batch`** | 降低多步任务的往返与重读成本 | 服务端批处理语义、部分失败的返回 |
| **受限 code mode** | 更复杂的编排 | 沙箱、审计、审批粒度；视度量再定 |
| **分发** | 源码构建之外的安装方式 | 打包、签名/公证、权限引导；等真实应用覆盖扩大后再做 |

**建议顺序**：截图 + 坐标（指示层；OCR 暂不做）→ 滚动/拖拽 → 应用启动/窗口 → 连接级应用允许列表 →
逐次审批（视参考实现证据与需要）→ `batch` → 视度量决定 OCR 与受限 code mode。
分发放在真实应用覆盖足够之后，`v1` 已明确不做。

**OCR 的位置**：它把文字变成候选框，不是"找按钮"的核心机制。v2 第一版不做，因为 AX 覆盖大部分应用、
CEF 可用启动参数、剩下的非 AX 场景多为图标/画布；只有当坐标点击在文字目标上的失败率被测量证明高时，
才把它作为候选层加上。

## 取舍

**放弃了先验证再投入的保守性。** 若身份假设不成立，P0 中围绕身份写的协议层代码
有一部分要重写。接受这一点，是因为隔离的存在使重写范围有界，
且这部分代码本来就是验证的载体，不是额外成本。

**接受了 P0 期间实现与假设同时漂移。** 边写边验证容易让实现迁就样本。
缓解办法是门槛提前冻结，并把验证结论写进 `verification/`，而不是只留在代码里。

**接受了 Swift 工具链的绑定。** 协议层与未来的 JS 运行时（[运行时契约](../interfaces/runtime_contract.md)）
可能不同语言，该选择仍然待定，不由本决策限定。

## 后果

- [本地环境](../operations/local_setup.md)不再要求先建立 Python 验证环境
- `Package.swift` 与 `Sources/` 成为仓库的一部分，文档需区分"已实现行为"与"拟实施设计"
- 新增构建与测试步骤，见本地环境
- [测试策略](../operations/testing.md)的假设表仍然有效，执行时机改为 P0 内
- 原生层语言不再是[系统总览](../architecture/system_overview.md)中的待定项
