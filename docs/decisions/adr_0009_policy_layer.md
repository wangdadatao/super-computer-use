# ADR-0009 策略层独立成层，不散落在各层之中

- **状态**：已接受
- **日期**：2026-10-16

## 外部观察来源

本文涉及对两套已发布实现的观察结论。来源、具体证据与复核方法见
[verification/external-sources.md](../../verification/external-sources.md)。

## 背景

桌面自动化能触达的能力边界很宽：读写任意应用的任意控件、
触发菜单、操作终端、访问密码管理器。
**没有任何一个真实实现把这件事完全交给模型判断。**

但两套参考实现选择了不同的约束方式：

| 实现 | 方式 | 特点 |
| --- | --- | --- |
| Codex Computer Use | 写入模型提示词的审批策略 + 运行时审批界面 | 细粒度、可表达复杂条件、依赖模型遵守 |
| Grok Bot Computer Use | 硬编码的应用黑名单 + 逐应用三态决策 | 不可绕过、粒度粗、需要维护应用清单 |

观察到的具体机制：

- 提示词侧的策略以编号条目组织，覆盖绕开安全提示、保存凭据、
  安装软件、授权摄像头与麦克风、发送消息等类别，并要求在特定动作前请求用户确认
- 运行时会弹出审批界面，并在会话级与持久级分别记录已批准的应用
- 硬编码侧则维护了若干类别（运行 shell 的应用、运行脚本的应用、
  持有密码的应用、系统设置、以及实现自身），命中即拒绝并附带固定说明

两者并非互斥。硬编码黑名单解决"绝不该发生的事"，
提示词策略解决"需要视情况判断的事"。**它们的适用区间不同。**

## 决策

**SCU 引入独立的策略层，不把策略判断散落在接入层、协议层或原生层。**

判定位置：**在协议层解析出目标之后、执行动作之前。**
本文最初写作“位于接入层与协议层之间”，审计发现这不可实现——
策略判定需要目标应用标识，而动作请求里的元素引用不含应用身份，
目标只存在于会话的绑定状态中。判定必须等目标确定后才能进行。
代价是被拒绝的动作已过了一次令牌校验（一次版本号比较，无副作用）。

策略层**不持有状态**：判定所需的全部信息（含目标标识）
由协议层解析后作为参数传入，策略层不读会话、不缓存任何东西。

策略层职责：

- 决定某个动作**是否允许**、**是否需要用户确认**、还是**直接拒绝**；
  写操作逐次判定，读操作不过准入（“能读哪个应用”由绑定时的授权决定）
- 维护不可绕过的拒绝类目（对应"绝不该发生"）
- 维护需要用户逐次确认的动作类目（对应"视情况判断"）
- 记录审批状态及其作用域

策略层的判定结果是一个**三态结论**：允许 / 需确认 / 拒绝。

策略层**不做**的事：

- 不决定"用户想做什么"——它不知道意图，只判断动作本身
- 不修改动作内容——它要么放行原动作，要么拒绝，不做替换或降级
- 不感知具体平台——策略描述的是动作语义，不是平台 API

## 取舍

**接受了额外一层带来的复杂度。** 每个动作都要经过策略判定，
调用链变长，且策略层需要理解动作语义——这意味着它与协议层的数据模型耦合。

**接受了硬编码清单的维护成本。** 拒绝类目中的具体应用清单
（哪些应用运行 shell、哪些持有密码）会随生态变化而过时。
选择保留这份清单是因为它防护的是不可逆的后果。

**放弃了策略的完全表达能力。** 三态结论无法表达"在 X 条件下允许，
在 Y 条件下需确认"这类复合条件。需要这类表达时，
只能在策略层内部实现，不暴露给调用方。

## 后果

- [系统总览](../architecture/system_overview.md)的分层从三层变为四层
- 动作的返回值需要能表达"被策略拒绝"，与"被协议拒绝（令牌失效）"
  区分开，否则调用方无法判断该重试还是该求助
- 策略层需要配置面，且用户应当能审计当前生效的策略
- 策略层成为安全边界，需要专门的测试覆盖
