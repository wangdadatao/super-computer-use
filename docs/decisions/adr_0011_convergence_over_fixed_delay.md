# ADR-0011 动作后用收敛判定，而非固定延时

- **状态**：已接受
- **日期**：2026-10-16

## 外部观察来源

本文涉及对两套已发布实现的观察结论。来源、具体证据与复核方法见
[verification/external-sources.md](../../verification/external-sources.md)。

## 背景

[ADR-0006](adr_0006_action_effect_verification.md) 要求动作返回效果摘要，
其中"疑似空操作"字段用于识别"事件投递了但什么也没发生"。
这个字段的准确性完全取决于**在什么时刻判断**。

判断太早会把"还没变"误判为"没变"；判断太晚浪费时间。
两套参考实现分别处理了这个问题，但方式不同：

| 实现 | 方式 |
| --- | --- |
| Codex Computer Use | 动作后自动等待，据其文档描述约一秒，若应用有加载迹象则延长至数秒 |
| Grok Bot Computer Use | 提供显式的等待原语，语义是"等待页面加载或动画稳定"，默认一千毫秒 |

前者的行为是隐式的，调用方不需要知道等待的存在；
后者是显式的，调用方自己决定何时等待。

**两者都不精确**——都是启发式的固定量级，不是真的检测"稳定了"。

## 决策

**SCU 在动作内部做有界收敛判定，同时提供显式等待原语。**

- 动作执行后，服务端在**有界窗口内**观察目标是否进入稳定状态
- 稳定的判定基于可观测信号：无障碍树的变更通知停止、
  或已声明的加载状态结束
- 若窗口内未观察到稳定，不阻塞等待到超时，而是立即返回，
  并在效果摘要中标明"尚未收敛"
- 另提供显式等待原语，供调用方在已知需要等待时使用

关键区别：**效果摘要里区分"没有变化"和"还没稳定"。**
这两个状态对调用方的含义完全不同——前者应当重新考虑策略，
后者应当继续等待。

## 取舍

**接受了实现复杂度。** 收敛判定需要订阅无障碍树的变更通知，
并维护一个逐目标的观察窗口。这比"固定 sleep 一秒"复杂得多。

**接受了判定仍不完美。** 有些应用的加载状态不会暴露在无障碍树里，
有些动画没有可观测的结束信号。这些情况下判定会退化为固定超时。

**放弃了"永远等够"的确定性。** 有界窗口意味着总有一个上限，
超过上限就返回未收敛。这是刻意的：无限等待会让调用方无法区分
"应用卡住了"和"应用还在加载"。

## 后果

- 效果摘要需要增加"是否已收敛"的维度，与
  [ADR-0006](adr_0006_action_effect_verification.md) 的字段定义需要一并修订
- 原生层需要暴露无障碍树的变更通知，而不只是提供读取接口
- 调用方需要理解三态：已稳定但无变化 / 未稳定 / 已稳定且有变化
- [测试策略](../operations/testing.md)需要增加收敛判定的用例，
  覆盖"慢应用"与"无加载信号的应用"

## 追加记录（2026-10-18，P0 的最小收敛判定）

P0 没有实现上文的变更通知与观察窗口（原生层目前没有通知），点击之后用**轮询重读**近似，
这是[快照生命周期](../architecture/snapshot_lifecycle.md#p0_implementation)"动作时比对"在动作之后的对应物：

| 参数 | 值 | 性质 |
| --- | --- | --- |
| 轮询间隔 | 200 毫秒 | **启发式初值，没有数据支持** |
| 收敛条件 | 连续两次重读的结构摘要一致 | 摘要口径同令牌（排除几何） |
| 总上限 | 3 秒 | **启发式初值，没有数据支持**；达到上限返回 `converged=false` |

已知局限（实现已如实反映在返回里，不是被掩盖）：

- 两次一致只说明这 400 毫秒内没变，不说明加载已结束；没有加载信号的应用会被误判为已收敛。
- 重读成本随树大小线性增长：访达列表视图约 1.5 万个元素时一次重读约 5 秒，已超过 3 秒上限，
  此时只做一次重读就停止，`converged=false`。
- 树被预算截断时，两次读取的截断位置可能不同，无法比较：`treeChanged` 报 `unknown`，不报"没变"。
- 三态里"已稳定但无变化 / 未稳定 / 已稳定且有变化"分别对应 `noOpSuspected=true`、`converged=false`、`treeChanged=true`。

阈值是否合适由验证阶段的"收敛判定验证"场景度量后修订；在那之前不得声称它们经过验证。
