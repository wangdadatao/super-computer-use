# ADR-0003 失效检测作为协议契约而非调用约定

- **状态**：已接受
- **日期**：2026-10-16

## 背景

元素引用在界面变化后会失效。两种处理方式：

**调用约定**：由文档或提示词要求调用方"每次动作后重新读取状态，
不要复用旧引用"。观察到的 Codex Computer Use 采用这种路线——
其能力说明中明确要求每步动作后重新读取，并解释理由是强制重新推导
元素编号而非复用过期值。

**协议契约**：服务端签发版本令牌并跟踪有效性，在令牌失效时
主动拒绝动作并上报。观察到的 Grok Bot Computer Use 采用这种路线——
状态读取返回快照令牌，截图返回坐标令牌，动作请求携带令牌，
失效时返回结构化的失效错误并说明需要重新读取。

两者都可以"工作"。差别在于失败模式：

- 调用约定下，模型忘记刷新时会**静默操作到已错位的目标上**。
  界面不会报错，动作看起来成功，只是点错了地方。
- 协议契约下，模型忘记刷新时会**收到一次明确的拒绝**，可以立即纠正。

## 决策

**SCU 采用协议契约。**

- 每次状态读取签发快照令牌，每次截图签发坐标令牌
- 动作请求必须携带令牌，坐标类动作的令牌为必填
- 令牌失效时**拒绝执行**，返回结构化的失效类别（树变化 / 窗口变化 / 目标切换）
- 不设绝对过期时间（TTL）。失效完全由状态变化驱动

## 取舍

**放弃了便利性。** 令牌机制要求调用方每次都传递并更新令牌，
比"直接给坐标"多一步。对简单的一次性操作，这个开销是纯负担。

**接受了失效判定的实现成本。** 服务端需要在动作到达时比对当前状态
与令牌对应的状态。这要求维护快照缓存并保证比对准确——
比对错误会导致误拒（把有效令牌判为失效）或漏拒（放行过期令牌）。

**接受了存在窗口期。** 服务端不主动轮询界面，因此界面变化与
服务端察觉之间存在时间差。在这个窗口期内，调用方带旧令牌的动作
会被拒绝。这是刻意的设计：代价是一次可重试的拒绝，
而不是一次无法察觉的错误操作。

## 后果

- [快照生命周期](../architecture/snapshot_lifecycle.md)成为协议层的核心复杂度来源
- 调用方必须理解令牌语义，接入层的文档和 SDK 需要把这一点讲清楚
- 与 [ADR-0004](adr_0004_stable_element_identity.md) 的分工必须明确：
  令牌负责"数据是否过期"，身份负责"过期后能否找回"
