## 为什么需要令牌

SCU 把"调用方手上的数据是否还有效"变成服务端可回答的问题。做法是：
每次读取状态时签发一个令牌，并在令牌不再可用时**主动告诉调用方**。

这取代了"请调用方记得每次重新读取"的约定。约定依赖调用方自律，
令牌是协议保证。

## 两种令牌

### 快照令牌（snapshot token）

代表一次**无障碍树读取**的版本。

- 在返回元素表时签发
- 在整个树未变化期间保持有效，可跨多次动作使用
- 树发生变化、窗口切换、目标应用退出时失效

### 坐标令牌（coordinate token）

代表一次**屏幕或窗口捕获**的几何基准。

- 在返回截图时签发
- 在窗口移动、缩放或重新截图前有效
- 与快照令牌相互独立：没有读取过树也可以有坐标令牌

两者分开的原因是失效条件不同。窗口移动会让所有基于像素的坐标失效，
但树结构可能完全没变；反过来，列表刷新会让树失效，而窗口几何不变。

## 状态迁移

```
              ┌──────────┐
   签发 ─────▶│  fresh   │ 令牌有效，元素引用可直接使用
              └────┬─────┘
                   │ 动作执行 / 时间推进
                   ▼
              ┌──────────┐
              │  used    │ 仍然有效；期间若检测到变化则转 stale
              └────┬─────┘
                   │ 检测到触发条件
                   ▼
              ┌──────────┐
              │  stale   │ 令牌失效，元素引用不可再用
              └──────────┘
```

**`used` 是乐观状态。** 服务端不主动轮询界面来判断是否变化——那样成本过高。
它在**下次交互时**检测：调用方带着旧令牌发起动作，服务端比对当前状态，
发现不符则拒绝执行并回报失效。

这意味着存在一个窗口期：界面变了但服务端还不知道。设计上接受这个窗口期，
因为代价是"一次被拒绝的动作"，而不是"一次静默的错误动作"。

## 判定机制

本节回答“服务端如何得知状态已变”。这是整套可靠性的地基，也是实现时
需要写的第一个核心函数。

### 树版本号

原生层为每个目标维护一个**单调递增的版本号**。令牌携带签发时的版本号，
动作到达时比较。以下变化使版本号递增：

| 变化 | 递增 | 理由 |
| --- | --- | --- |
| 节点增删、层级调整 | ✓ | 位置寻址必然失效 |
| `role` / `subrole` / `title` / `value` / `enabled` 变化 | ✓ | 影响元素表内容与身份匹配 |
| 焦点变化 | ✓ | 影响元素表的 `state` 字段 |
| 几何变化（位置、尺寸） | ✗ | 只影响[坐标令牌](#两种令牌)，不影响树 |

把几何排除在外是刻意的：否则窗口拖动会让全部树令牌失效，
而树本身根本没变。

### 驱动来源：变更通知

版本号由**平台的无障碍变更通知**驱动，不做主动轮询。

轮询的成本随界面复杂度线性上升（每次轮询都是跨进程的属性读取），
而绝大多数动作发生在界面静止期间——轮询在那些时刻是纯浪费。

通知驱动还有一个副作用是正面的：**它同时是
[收敛判定](../architecture/action_convergence.md) 的输入**。两套机制共享同一条
通知流，不需要各建一套。

### 通知不可靠，且无法完全弥补

变更通知是异步且可能丢失的。这带来一个窗口期：**界面已变，
但服务端仍认为令牌有效。**

两种故障模式：

| 故障 | 表现 | 后果 |
| --- | --- | --- |
| 通知延迟 | 到达晚于动作请求 | 本次动作可能投向错位的元素 |
| 通知丢失 | 版本号永不递增 | 失效永不被检测，持续失效 |

**设计上接受窗口期，但不接受第二种故障。** 缓解手段是一道可选的**强校验**：

- 调用方可在关键动作前请求强校验
- 强校验主动走一次树，计算一个**结构摘要**（根节点子节点数 + 树深度 + 元素总数）
- 与上次记录的摘要不符则判定失效，并补偿性地递增版本号

强校验的成本高于通知，因此不是默认行为。它适用于“这一步不能错”的场景，
由调用方权衡。

**需要明确记录的局限**：不存在零成本且完全可靠的变更检测。
在通知与强校验都未覆盖的时刻，误判是可能的。这属于设计上的已知缺口，
而不是实现缺陷。

## 失效上报

失效必须**结构化上报**，而不是让调用方从错误文本里猜：

- 动作被拒绝时，明确区分「令牌失效」和「其他错误」
- 令牌失效时同时说明失效原因类别（树变化 / 窗口变化 / 目标切换）
- 请求携带的令牌与当前令牌一致时，不重复上报失效

原则：**宁可拒绝执行，也不执行到错误的目标上。** 一次被拒绝的动作，
调用方可以重试；一次点错位置的点击，调用方可能永远不会发现。

## 与元素身份的分工

两者解决不同层次的问题，必须同时存在：

| | 解决 | 失效后 |
| --- | --- | --- |
| 快照令牌 | 快速判断"数据是否过期" | 拒绝动作，要求重读 |
| 元素身份 | 过期后"还能不能找回这个元素" | 在新快照中重新匹配 |

只有令牌，界面一变调用方就得完全重来；只有身份，服务端无法判断手上的
引用是否还有效。两者叠加的效果是：**界面稳定时零成本，界面变化时可恢复。**
