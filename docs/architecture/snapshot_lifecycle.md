## 为什么需要令牌

SCU 把"调用方手上的数据是否还有效"变成服务端可回答的问题。做法是：
每次读取状态时签发一个令牌，并在令牌不再可用时**主动告诉调用方**。

这取代了"请调用方记得每次重新读取"的约定。约定依赖调用方自律，
令牌是协议保证。

## 两种令牌

### 快照令牌（snapshot token）

代表一次**无障碍树读取**的版本。

- 在返回元素表时签发
- 在整个树未变化期间保持有效，可跨多次动作使用
- 树发生变化、窗口切换、目标应用退出时失效

### 坐标令牌（coordinate token）

代表一次**屏幕或窗口捕获**的几何基准。

- 在返回截图时签发
- 在窗口移动、缩放或重新截图前有效
- 与快照令牌相互独立：没有读取过树也可以有坐标令牌

两者分开的原因是失效条件不同。窗口移动会让所有基于像素的坐标失效，
但树结构可能完全没变；反过来，列表刷新会让树失效，而窗口几何不变。

## 状态迁移

```
              ┌──────────┐
   签发 ─────▶│  fresh   │ 令牌有效，元素引用可直接使用
              └────┬─────┘
                   │ 动作执行 / 时间推进
                   ▼
              ┌──────────┐
              │  used    │ 仍然有效；期间若检测到变化则转 stale
              └────┬─────┘
                   │ 检测到触发条件
                   ▼
              ┌──────────┐
              │  stale   │ 令牌失效，元素引用不可再用
              └──────────┘
```

**`used` 是乐观状态。** 服务端不主动轮询界面来判断是否变化——那样成本过高。
它在**下次交互时**检测：调用方带着旧令牌发起动作，服务端比对当前状态，
发现不符则拒绝执行并回报失效。

这意味着存在一个窗口期：界面变了但服务端还不知道。设计上接受这个窗口期，
因为代价是"一次被拒绝的动作"，而不是"一次静默的错误动作"。

## 失效上报

失效必须**结构化上报**，而不是让调用方从错误文本里猜：

- 动作被拒绝时，明确区分「令牌失效」和「其他错误」
- 令牌失效时同时说明失效原因类别（树变化 / 窗口变化 / 目标切换）
- 请求携带的令牌与当前令牌一致时，不重复上报失效

原则：**宁可拒绝执行，也不执行到错误的目标上。** 一次被拒绝的动作，
调用方可以重试；一次点错位置的点击，调用方可能永远不会发现。

## 与元素身份的分工

两者解决不同层次的问题，必须同时存在：

| | 解决 | 失效后 |
| --- | --- | --- |
| 快照令牌 | 快速判断"数据是否过期" | 拒绝动作，要求重读 |
| 元素身份 | 过期后"还能不能找回这个元素" | 在新快照中重新匹配 |

只有令牌，界面一变调用方就得完全重来；只有身份，服务端无法判断手上的
引用是否还有效。两者叠加的效果是：**界面稳定时零成本，界面变化时可恢复。**
